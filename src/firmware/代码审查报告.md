**结论**：GPIO 分配与 README/MEMORY 完全一致，**未发现错配**。

**补充观察**：
- GPIO0、GPIO1 在 ESP32-C3 上属于 strapping pin（启动时电平决定启动模式），用作 I2C 上下拉后通常不会影响启动，但项目 MEMORY.md 强调"DS18B20 必须用 GPIO7 避开 strapping pin"，对 OLED I2C 没有同等程度的保护说明，建议硬件上确认外部上拉强度。
- `MEMORY.md` 第 16 行记录的 GPIO6（加热棒继电器预留）在 `config.h` 中**未定义宏**，是文档占位，无代码实现，与"原型阶段不实现"的设计决策一致。

### 1.2 OLED 尺寸

| 来源 | 描述 |
|------|------|
| `README.md`（项目根）| "OLED 0.66" I2C 接口" |
| `MEMORY.md` | "0.66寸 I2C SSD1306" |
| `src\firmware\README.md` | "OLED 0.66 寸"（隐含） |
| `config.h` | `OLED_ADDRESS 0x3C`，注释"SSD1306 I2C 地址" |
| `main.ino` | `#include <SSD1306Wire.h>` + `new SSD1306Wire(OLED_ADDRESS, SDA, SCL)` |

**结论**：OLED 类型/尺寸在文档中**一致为 0.66 寸 SSD1306**。

**潜在问题**（⚠️ 非错配，但需注意）：
1. **0.66 寸屏常见分辨率是 64×48**，而 `SSD1306Wire` 库构造函数默认 `GEOMETRY_64_32` 或 `GEOMETRY_128_64`（取决于库版本）。代码未显式指定 geometry，可能与硬件实际分辨率不匹配。
2. `updateOLED()` 中第 4 行 `oled->drawString(0, 48, line4)`：在 64×48 屏上，y=48 baseline 配合 ArialMT_Plain_10 字体（高 ~10px）可能**部分越出可见区域**。建议确认屏实际分辨率。
3. 0.66 寸 OLED 市场上有 **SSD1306 和 SH1106 两种驱动芯片**混用的情况。若硬件实际是 SH1106 而代码用了 SSD1306Wire，会出现显示偏移或内容错位。

### 3.4 真实功能 Bug

#### 🔴 问题 8：webpage.h `setColor` 函数丢前导 0 导致颜色失真

`webpage.h` 第 422-432 行：
```javascript
function setColor(color) {
    currentLedColor = color;
    ...
    fetch('/api/led?brightness=' + currentBrightness + '&color=' + color.toString(16))
}
```

`setBrightness`（第 415-420 行）也用 `currentLedColor.toString(16)`：
```javascript
fetch('/api/led?brightness=' + value + '&color=' + currentLedColor.toString(16))
```

`main.ino:242` 服务器解析：
```cpp
g_systemState.ledColor = strtoul(request->getParam("color")->value().c_str(), NULL, 16);
```

**Bug 复现**：
- 用户选择绿色 `0x00ff00`（R=0, G=255, B=0）
- JS `color.toString(16)` → `"ff00"`（丢前导 0！）
- 服务端 `strtoul("ff00", NULL, 16)` → `0xff00`（R=255, G=255, B=0 = **黄色**）
- **绿色经过一次设置后变成黄色**

**影响**：凡是颜色分量高位为 0 的颜色（绿色 `0x00ff00`、蓝色 `0x0000ff`、纯色低分量）都会失真。

**修复建议**：JS 端在 toString(16) 后补足 6 位（如 `('00000' + color.toString(16)).slice(-6)`），或服务端在 strtoul 后补 0。

#### 🔴 问题 9：`getStatusJSON` 颜色回传同样丢前导 0

`main.ino:535`：
```cpp
json += "\"color\":\"" + String(g_systemState.ledColor, HEX) + "\",";
```

Arduino `String(int, HEX)` 不补零。对 `0x00ff00` 输出 `"ff00"`。前端 `setBrightness`/`setColor` 读回后用 `parseInt(..., 16)`，又变回 `0xff00`，形成**持续的颜色漂移**：绿色会被固化成黄色，且无法回退。

**影响**：与问题 8 是同一根因的"另一半"。两者都修才能闭环。

#### 🟡 问题 10：定时器状态机 `lastLightCheck` 跨天/重配置处理不健壮

`main.ino:442-454`：
```cpp
if (g_scheduleConfig.autoLightEnabled) {
    if (currentHour == lightOnHour && currentMin == lightOnMinute && !lastLightCheck) {
        controlLed(true, ...);
        lastLightCheck = true;
    } else if (currentHour == lightOffHour && currentMin == lightOffMinute && lastLightCheck) {
        controlLed(false, 0, 0);
        lastLightCheck = false;
    }
}
```

**问题场景**：
1. **跨天配置**：若用户设 `lightOnHour=20, lightOffHour=8`（夜灯模式），20:00 开灯后 `lastLightCheck=true`；次日 08:00 条件 `!lastLightCheck` 为 false，**不会触发关灯**。直到 20:00 才进入关灯分支——但因 `currentHour=20=lightOnHour` 而非 `lightOffHour=8`，**永远关不掉**。
2. **重配置**：用户白天调时间把 `lightOnHour` 从 8 改到 9，若 `lastLightCheck` 还为 true（即在 8:00 之前已经开过灯），后续 9:00 因 `!lastLightCheck=false` 不会触发开灯逻辑。

**喂食定时（`lastFeedDone`）** 处理得更好——有 `else if (currentMin != feedMinute) lastFeedDone = false;` 重置。光控分支没有对应重置。

**影响**：特殊配置或修改时间时灯光可能卡在错误状态。

#### 🟡 问题 11：NTP 失败时 `bootTime` 为 0 导致 `uptime` 异常

`main.ino:378-389`：
```cpp
void initTime() {
    configTime(NTP_TIMEZONE * 3600, 0, NTP_SERVER);
    if (getLocalTime(&g_timeinfo)) {
        g_lastNtpSync = time(nullptr);
        ...
    } else {
        Serial.println("[Time] NTP 同步失败");
    }
    g_systemState.bootTime = time(nullptr);  // ← NTP 失败时此值为 0（1970-01-01）
}
```

若 NTP 同步失败（例如首次启动没有 WiFi、AP 模式下）：
- `time(nullptr)` 返回 0
- `g_systemState.bootTime = 0`
- `getStatusJSON()` 中 `uptime = time(nullptr) - 0` 在系统运行一段时间后是"自 1970 起的秒数"，前端 `updateStatus()` 把它当秒数除以 86400 → 显示"运行时间: 1850天..."。**无意义的负值或巨大值**。

**影响**：AP 模式下用户访问 192.168.4.1 会看到"运行时间"显示"1970 距今多少年"，误导严重。

**修复建议**：用 `millis()` 计算 uptime（NTP 无关），或在没有 NTP 时用本地 RTC 兜底。

### 3.5 性能与健壮性

#### 🟡 问题 12：喂食时阻塞 WebServer 3 秒

`main.ino:513-522`：
```cpp
void feedFish() {
    Serial.println("[Feed] 开始喂食...");
    g_servo.write(90);
    delay(FEED_DURATION);  // 3000ms 阻塞
    g_servo.write(0);
    ...
}
```

`/api/feed` 端点直接调用 `feedFish()`，期间 ESP32 的 loop() 被 `delay(3000)` 阻塞，**WebServer 无法响应其他请求**，且定时任务 `checkSchedule()`、OLED 更新、温度读取全部停摆。

**影响**：
- 同时点击"喂食"和"水泵"时，水泵 API 要等 3 秒才响应。
- 3 秒内定时任务错过分钟边界可能漏触发。

**修复建议**：用 `millis()` 状态机实现非阻塞喂食，或在喂食时把舵机动作分多次在 loop 中推进。

#### 🟡 问题 13：高频 NVS 写影响 Flash 寿命

`main.ino` 中每次 `/api/led`、`/api/pump`、`/api/config` 都会调用 `saveConfig()` → `g_preferences.putXxx()`，每次写入都会触发 NVS commit。

**影响**：
- ESP32 的 NVS 默认有磨损均衡，但频繁写仍会缩短 flash 寿命。
- 每次写入还有几毫秒延迟，挤占 loop 周期。

**修复建议**：节流（如 5 秒内多次写只保留最后一次）、或加 dirty flag 在 `loop()` 空闲时统一写。

#### 🟢 问题 14：`String json` 使用 static 局部对象

`main.ino:528`、`main.ino:548`：
```cpp
String getStatusJSON() {
    static String json;  // 多请求并发时竞争
    json = "{";
    ...
}
```

`AsyncWebServer` 在另一 task 中调用这些函数（虽然 ESP32-C3 是单核，core 0 跑系统，loop 在 core 1 单线程）——在单核 ESP32-C3 上目前是安全的，但**不正确的模式**。如果未来加 FreeRTOS 任务或改用双核芯片，会引入隐蔽的竞争。

#### 🟢 问题 15：`webpage.h` 中 `event.target` 在严格模式可能未定义

`webpage.h:425`：
```javascript
function setColor(color) {
    ...

```

全局变量 `event` 在严格模式（`"use strict"`）下未声明。代码目前未启用 strict mode（无 `"use strict"`），所以**当前能工作**，但维护时不安全。

#### 🟢 问题 16：OLED 字体与 0.66 寸屏匹配度

`main.ino:370`：`oled->setFont(ArialMT_Plain_10);`

ArialMT_Plain_10 字符宽度约 6-7px、高约 10px。在 64×48 屏上，4 行字（0/16/32/48）总高 58px > 48px，**第 4 行会越界**。即使 128×64，第 4 行 y=48 + 10 ≈ 58px 也接近底部。

**影响**：在 0.66 寸屏（64×48）上，最后一行"IP"信息可能**部分不可见**。
